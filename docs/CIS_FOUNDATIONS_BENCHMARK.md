# CIS AWS Foundations Benchmark v7.0.0 — coverage

**All 70 recommendations, and what OverWatch does about each.** Nothing is listed as
covered without naming the check that covers it, and a check that cannot FAIL is never
counted as covering anything — it can tell you a setting's value, but it can never tell an
operator they are non-compliant.

> **On the source document.** CIS Benchmarks may not be redistributed, and the PDF is
> deliberately not in this repository — the document's own terms state it is never
> acceptable to host a CIS Benchmark in any format on a non-CIS site. What is cited below
> is the recommendation *number*, which is a reference, together with a one-line label
> written from the underlying AWS behaviour. No title, rationale, audit, impact or
> remediation text is reproduced.

**GENERATED by `scripts/cis_foundations_benchmark.py` from
`engine/aws_cis_foundations_map.py`. Do not hand-edit.**

## How to read the verdicts

| Verdict | Meaning |
|---|---|
| covered | A named check decides it and can FAIL on it. |
| narrowed | A check decides a defensible *subset* and can FAIL on it; the rest is not readable from the control plane, and the finding says which half it settled. |
| observed only | A check reads the setting and reports it, but never FAILs. Coverage of the observation, not of the finding. |
| decided elsewhere | The same check answers this and a neighbouring recommendation in one read. Keyed on the neighbour so one check is not counted as two coverages. |
| **gap** | Decidable from the control plane today, and not checked. |
| process | Asks about a human process. No API read can decide it. |
| vacuous | True of every modern account by construction. |

## The edition matters more than usual this time

Every `CIS` citation in this product used to read against **v3.0**, and the framework
registry said so. That was honest, not stale — but v7.0.0 renumbers *every* section, so an
estate audited against the current document could not reconcile a single OverWatch
citation with it. Section 1 is now the Introduction and carries no recommendations at all,
which means every `1.x` citation the product used to emit now points at nothing.

The move is not a uniform shift. IAM 1.x becomes 2.x, Storage 2.x becomes 3.x, Logging 3.x
becomes 4.x, Monitoring 4.x becomes 5.x and Networking 5.x becomes 6.x — but *inside* IAM
two recommendations were eliminated on the way, so 1.12 lands on 2.11 and 1.14 on 2.12.
Anyone assuming a constant offset would mis-cite both. The full table is `RENUMBERED` in
`engine/aws_cis_foundations_map.py`.

## What the mapping found, and what was done about it

Mapping a document line by line is an unusually thorough read of it, and reading it
against a catalogue of 554 checks is an unusually thorough read of the catalogue. Four
things came out of it.

**Nineteen recommendations had no check, and now have one.** They are marked ★ above.
Thirteen are new because the *recommendation* is new: v7.0.0 adds the whole Organizations
subsection, a cross-service resource-policy control, access logging on AWS-managed HTTP
front ends, VPC endpoints and SMB. The rest were older recommendations this product had
simply never reached — CloudTrail log file validation, the support role, MFA Delete.

**Fifteen of the nineteen answer a *Manual* recommendation.** That is the result worth
reporting. The benchmark marks a recommendation Manual when it does not believe one API
read settles it, and an auditor pays for each one in console time. Where the control plane
does in fact answer the question — and for centralized root access, the security contact,
delegated administration and MFA Delete it answers it outright — automating it is worth
more than automating an Automated one.

**Thirty citations were wrong against v3.0 as well, and are removed rather than
renumbered.** These are listed in full below. Each rendered as a well-formed reference
into a real document, at a control about something else — which is exactly the failure
mode that survives review, because the number looks plausible. The largest single group
was the privilege-escalation family: all seventeen IAMPE primitives carried 1.16, the
`*:*` administrative-privileges control. Exactly one of them decides it. The rest fire on
a principal that could *become* an administrator, which is a different and usually more
urgent finding, and one this benchmark has no recommendation for.

**Thirteen checks carried CIS *Kubernetes/EKS* numbering under the Foundations key.** 4.1.1,
4.1.3, 5.4.1 and the rest are coherent — against a different CIS document. v7.0.0's
section 4 is a flat Logging list and its section 5 a flat Monitoring list, so none of them
can be Foundations numbers. They are removed rather than re-keyed to a new `CIS-EKS`
framework, deliberately: this repository does not hold the EKS benchmark, and registering
a framework whose numbering nobody here has checked against its source would replace a
citation that is provably wrong with one that is merely unverified — which is worse,
because it reads as confirmed. The numbers are kept as data in
`aws_cis_foundations_map.EKS_NUMBERED` so the work is not lost.

**Twelve checks were doing the work and not claiming it.** EFS-01 has decided EFS
encryption at rest since long before this mapping and carried no `CIS` key at all; ACM-01
decides 2.17 exactly, and v7.0.0 rescoped that recommendation to ACM; ELB-01, CFN-04,
APIGW-01 and AGW2-01 together decide the new 4.10. Unclaimed coverage is the quieter half
of a mapping error and it costs a real estate real audit findings.

## One behavioural change came out of this, not just citations

v7.0.0's 5.10 adds `ModifySecurityGroupRules` to the metric-filter pattern for security
group changes. CW-11 required only `AuthorizeSecurityGroupIngress` and
`RevokeSecurityGroupIngress`, so it passed a filter that is blind to the API the AWS
console has used for rule edits since 2021. An estate that passed 4.10 under v6.0.0 can
legitimately fail 5.10 here, and that is the finding rather than a false positive: their
alarm does not fire on the way most security-group changes are actually made.

Two other v7.0.0 semantic changes needed no work, and it is worth recording why. 6.2 now
accepts an effective ruleset — a DENY ordered before a broad ALLOW closes the finding —
and VPC-05 has always evaluated NACL rule order rather than matching the ALLOW alone. 4.3
now accepts AWS Config being centrally managed through Control Tower or a Landing Zone
Accelerator, which does not change what LOG-03 reads.

## What is deliberately not claimed

Three recommendations are answered only in part, and the rows above say so rather than
rounding up:

* **2.1.4** asks that organizational units be structured by environment and sensitivity.
  ORG-04 decides the objectively readable half — an account parented to the root is in no
  OU, so no OU-scoped guardrail can reach it. Whether `ou-prod-1` means production is a
  judgement about a name, and scoring it would be scoring a naming convention.
* **2.2** asks for contact details that are *current*. ACCT-01 decides *populated*. No API
  says whether a phone number still reaches anybody.
* **3.2.4** asks for Multi-AZ where availability warrants it, and declines to say that
  single-AZ is wrong. RDS-03 reads the setting and never fails on it, which is the right
  shape for a control whose own text does not prefer an answer.
