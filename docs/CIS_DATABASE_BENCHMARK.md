# CIS AWS Database Services Benchmark v2.0.0 — coverage

**All 98 recommendations across ten services, and what OverWatch does about each.**
Nothing is listed as covered without naming the check that covers it, and a check that
cannot FAIL is never counted as covering anything — it can tell you a setting's value, but
it can never tell an operator they are non-compliant.

> **On the source document.** CIS Benchmarks may not be redistributed, and the PDF is
> deliberately not in this repository. What is cited below is the recommendation *number*,
> which is a reference, together with a one-line label written from the underlying AWS
> behaviour. No rationale, audit, impact or remediation text is reproduced.

## How to read the verdicts

| Verdict | Meaning |
|---|---|
| covered | A named check decides it and can FAIL on it. |
| observed only | A check reads the setting and reports it, but never FAILs. Real coverage of the observation, not of the finding. |
| decided elsewhere | Answered outside these services — by the segmentation, CloudTrail or CIEM pillars — or, in one case, under an id that names the wrong service. |
| **gap** | Decidable from the control plane today, and not checked. This is the honest backlog. |
| declined | Deliberately not built, with the reason recorded in `engine/aws_cis_db.py` rather than left as silence. |
| process | Asks about a human process: a review cadence, a design exercise, a procurement decision. No API read can decide it. |
| vacuous | True of every modern account by construction, so a check would pass universally and measure nothing. |

## Why `CIS-DB` and not `CIS`

99 checks carry a `CIS` key and every one of them is CIS AWS **Foundations** numbering.
The service benchmarks reuse those section numbers for entirely unrelated controls —
Foundations 2.2 is the account contact record, Compute 2.2 is EBS encryption, Database 2.2
is Aurora encryption at rest. Folding them into one key would mis-cite every mapping in
both directions at once, so Database controls carry their own `CIS-DB` key, exactly as
Compute controls carry `CIS-COMPUTE`.

That first example changed when Foundations moved to v7.0.0 — 2.2 was CloudTrail log-file
validation and is now something else — while Database 2.2 did not move. A shared key would
have let an edition bump in one document silently re-point citations in another.

## Defects found in the benchmark itself

Mapping a document line by line is an unusually thorough read of it. These are errors in
the published benchmark, recorded because each one changes what a conscientious auditor
should do with the recommendation — not as criticism for its own sake.

**5.8, 5.9 and 5.10 are filed under ElastiCache but audit Amazon Keyspaces.** All three
sit in section 5, and all three instruct the reader to open the Amazon Keyspaces console
and select a keyspace. ElastiCache has no keyspaces. Read literally the three controls are
unperformable; read charitably, 5.8 duplicates 5.1 and 5.9 has no ElastiCache meaning at
all. This also explains the duplicate title in the next item.

**5.7 and 5.10 carry the same title.** Both are "Ensure Security Configurations are
Reviewed Regularly". 5.7 is the genuine ElastiCache one; 5.10 is part of the misfiled
Keyspaces block. An estate tracking compliance by title will silently collapse them.

**3.13 and 3.14 audit RDS with a cluster-only API.** Both tell the reader to run
`aws rds describe-db-clusters`. Most RDS estates are standalone instances, for which that
call returns an empty list — which reads as "no findings" rather than "wrong question".
`IAMDatabaseAuthenticationEnabled` and `DeletionProtection` are instance-level fields, and
RDS-08 and RDS-04 read them there.

**7.3 asks for something DocumentDB cannot do.** Its remediation walks the reader through
modifying encryption at rest on an existing cluster. DocumentDB fixes encryption at
creation; there is no modify path. The only real remediation is a snapshot-and-restore
into a new encrypted cluster, which is a materially different piece of work to plan.

**5.13 is unsatisfiable on Memcached.** The audit treats `SnapshotRetentionLimit = 0` as
non-compliant across all ElastiCache clusters, but Memcached does not support snapshots at
all, so every Memcached cluster fails permanently with no available fix. ELC-07 scopes
itself to replication groups, which is where the setting means something.

**10.10 carries leftover text from another control.** Its remediation defines a single
on-demand backup rule, then instructs the reader to "replace 35 with your retention time
for PITR" — a value and a concept that appear nowhere else in the control. The same
paragraph in 4.9, which does have a PITR rule, is where it belongs.

**2.8's audit contradicts its own service.** It tells the reader that setting the
retention period to 0 disables automatic backups. For an Aurora *cluster* the minimum is 1
and 0 cannot be set, so the state the control warns about is unreachable. AUR-07 therefore
fails below 7 days rather than at 0 — a check written to the literal text would never fire.

**Several recommendations ship with empty fields.** 3.1 and 3.2 have no Description and no
Rationale; 2.4, 2.5, 3.5–3.11 and others have an empty Remediation. 3.1 in particular
("choose the appropriate database engine") is a procurement exercise with no state to
audit, which its empty fields make plain.


## What the mapping found in OverWatch, and what was done about it

**The RDS instance loop scored Neptune and DocumentDB instances as RDS.** *Fixed.* This was
the same defect tranche 1 fixed for *clusters*, still present one level down. Neptune and
DocumentDB share the RDS control plane, so `rds:DescribeDBInstances` returns their
instances, and `_rds_instances()` applied no engine filter. Run against a single Neptune
instance the section produced four findings — RDS-01, RDS-02, RDS-03 and RDS-04 — none of
which said Neptune anywhere.

It was found by *running* the section rather than reading it. The first version of the test
that pinned it read the source for an engine filter and was fooled immediately: `_check_rds`
mentions both `Engine` and `NON_AURORA_CLUSTER_ENGINES` for reasons that have nothing to do
with filtering instances, so the text said "filtered" while the code was not.

The reason it could not simply be filtered is that it cut both ways:

* RDS-01 and RDS-04 **double-reported**. Cluster storage encryption was already reported as
  NEP-01 or DOCDB-02, and deletion protection as NEP-02 or DOCDB-04, so the same fact
  arrived twice under two ids with two different remediation commands.
* RDS-02 and RDS-03 were the **only** coverage of Neptune 9.8 and 9.9. Nothing else read
  public accessibility or backup retention for Neptune. Filtering the loop without adding
  Neptune checks would have deleted real coverage — exactly the trap tranche 1 avoided by
  expanding from zero new checks to six.

So the filter and the replacement checks shipped in one change: `_rds_instances()` now drops
an instance that positively declares another service's engine, and NEP-06 and DOCDB-07 read
`PubliclyAccessible` where it belongs. The filter is a **deny-list, not an allow-list**, for
the same reason `NON_AURORA_CLUSTER_ENGINES` is: an instance with an unrecognised or absent
`Engine` keeps being scored, so a new RDS engine is covered by default rather than silently
dropped the day AWS ships it.

**The four gaps worth closing are closed.** DocumentDB backup retention (7.9), Neptune IAM
authentication (9.4), Neptune audit logging (9.5) and Neptune Multi-AZ (9.11) each already
existed for a sibling service, and each reads a field the section's existing
`DescribeDBClusters` call already returns — so all four cost no additional API read and no
additional permission. Two of them are Neptune-only for a reason worth recording: the
service model shows DocumentDB clusters carry no `IAMDatabaseAuthenticationEnabled` and
DocumentDB instances carry no `MultiAZ`, which is independent confirmation of the *process*
verdict this mapping had already given DocumentDB 7.5.

NEP-08 is rated a step above its Aurora equivalent. On Aurora, IAM authentication being off
means static passwords — a credential-hygiene problem. On Neptune it means there is no
authentication at all, because the engine has no database users to have passwords: whatever
reaches the endpoint is authorised by the security group and by nothing else.


## Declines, in full

Held as data in `engine/aws_cis_db.py` so this document, the coverage tests and the inventory all read the same list.

- **`keyspaces-needs-a-data-read-grant`** — Amazon Keyspaces authorises its control-plane reads -- ListKeyspaces, ListTables and GetTable -- under cassandra:Select, and that is the SAME action that authorises reading table rows. AWS offers no metadata-only read action for the service, so covering it would mean adding an action to the scanning role that permits reading customer data. That crosses the read-only-of-CONFIG line this product's role is built on, and which tests/test_perm_ledger.py::test_the_additive_policy_contains_only_read_actions already enforces by excluding s3:GetObject and logs:StartQuery for exactly the same reason. The checks themselves would be straightforward -- pointInTimeRecovery.status and encryptionSpecification.type are both plain enums -- so this is a decision about the GRANT, not about feasibility. If it is ever wanted, it belongs in an opt-in permission block alongside the other data-plane reads rather than in the default policy

- **`qldb-everything`** — Amazon QLDB has NO service model in the pinned botocore at all -- boto3 cannot construct a client for it, so none of section 11 is buildable regardless of whether it would be worth building. AWS removed the service from the SDK. tests/test_cis_db_keyspaces_timestream.py asserts this rather than asserting the judgement, so if AWS ever restores the model the decision gets re-made instead of silently standing

- **`timestream-database-key-ownership`** — whether a Timestream database uses a customer-managed key or the AWS-managed one cannot be told from the API. Every database returns a KmsKeyId, and for the AWS-managed key that is still an ARN in the customer's own account with the same shape as a CMK -- there is no field distinguishing them and no alias in the response to match on. Guessing from the key id would be wrong in both directions

- **`elasticache-cluster-mode`** *(readable, judged not a finding)* — whether Redis cluster mode (sharding) is enabled is an architecture choice, not a posture setting -- a single-shard replication group is a legitimate and very common design, so reporting it would flag correct systems. The availability properties the recommendation is reaching for are covered by ELC-04 (automatic failover) and ELC-08 (Multi-AZ), which are settings rather than architecture
